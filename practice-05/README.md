## Эксперимент с очередями выполнения

До запуска `npm run example:order` записан прогноз порядка меток. Затем в пример добавлен собственный обработчик Promise (метка G), поставленный сразу после обработчика D и до вызова async-функции; прогноз для изменённого примера записан отдельно.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | `A, B, C, D, E, F` | Сначала весь синхронный код: A, B (начало async-функции выполняется синхронно до первого `await`), C. Затем микрозадачи в порядке постановки: D (обработчик Promise), E (продолжение после `await`). Таймер с задержкой 0 выполняется последним, F. |
| Фактический результат | `A, B, C, D, E, F` | Совпал с прогнозом. |
| Прогноз для примера с обработчиком G | `A, B, C, D, G, E, F` | G ставится в очередь микрозадач после D и до продолжения после `await`, поэтому выполняется между ними. |
| Фактический результат с G | `A, B, C, D, G, E, F` | Совпал с прогнозом. |
| Фактический результат без обработчика D | `A, B, C, E, F` | D исчез, порядок остальных меток не изменился. |

- **Синхронный код:** сообщения A, B (до первого `await`) и C.
- **Микрозадачи:** обработчики `then` (D, G) и продолжение async-функции после `await` (E).
- **Почему таймер с задержкой 0 выполняется не сразу:** `setTimeout` помещает обратный вызов в очередь задач (macrotask). Цикл событий сначала завершает текущий синхронный код и полностью обрабатывает очередь микрозадач, и только потом берёт следующую задачу таймера.
- **Изменится ли вывод при удалении обработчика Promise:** метка этого обработчика исчезнет, а относительный порядок остальных сохранится (проверено: `A, B, C, E, F`).

## Наблюдение за HTTP-ответом

`npm run example:fetch` при запущенном API.

| Свойство | Фактическое значение | Что означает |
|---|---|---|
| URL запроса | `http://127.0.0.1:5505/api/tasks?completed=false&priority=high` | Фильтры передаются в query-строке |
| Метод | `GET` | `fetch` без параметров выполняет GET |
| Статус | `200` | Сервер успешно обработал запрос |
| `response.ok` | `true` | Статус в диапазоне 200–299 |
| `Content-Type` | `application/json; charset=utf-8` | Тело ответа — JSON |
| id полученных задач | `[4, 13, 34]` | Невыполненные задачи высокого приоритета |
| `meta.filters` | `{ completed: false, priority: 'high', categoryId: null, q: '' }`, `meta.total = 3` | Сервер возвращает применённые фильтры |

Дополнительные запросы (скрипт на `fetch`, считаны статус, `ok`, тип содержимого и форма тела):

| Запрос | Статус | `ok` | `Content-Type` | Форма тела |
|---|---:|---|---|---|
| `/health` | 200 | true | `application/json; charset=utf-8` | `data: { status: "ok" }` |
| `/tasks/25` | 200 | true | `application/json; charset=utf-8` | `data` — объект задачи с `id` 25 |
| `/tasks/999` | 404 | false | `application/json; charset=utf-8` | `error: { code: "TASK_NOT_FOUND", message, details }` |

Статус 404 не приводит к исключению `fetch`: промис завершается успешно, а признак ошибки — `response.ok === false`. Поэтому HTTP-ошибки проверяются отдельно.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API на `node:http`: маршруты `/api/health`, `/api/tasks`, `/api/tasks/:id`, `/api/categories`, отладочные `/api/debug/*`. Менять не требуется. |
| `src/api-client.js` | Общий клиент: `ApiError`, `buildUrl`, `createApiClient` и `requestJson`: URL, тайм-аут и отмена, проверка статуса и типа содержимого, разбор JSON, преобразование ошибок. Знает про HTTP, но не про задачи. |
| `src/task-api.js` | Предметный слой: `createTaskApi(client)` с `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`; проверка фильтров до запроса и проверка ответов по схеме. |
| `src/variant.js` | Данные варианта: `variantNumber = 6`, `variantFilters = { categoryId: 2 }`. |
| `src/main.js` | Готовый консольный сценарий: вызывает `loadInitialData` с фильтрами варианта и контрольный запрос задачи 999, печатает таблицу и вид ошибки. |

- **Почему `fetchFn` передаётся в `createApiClient`:** тогда клиент можно проверить на подменённой функции без реальной сети (ответы, отказы, медленный ответ задаются в тесте), а в приложении используется настоящий `fetch`. Это явная зависимость вместо глобального состояния.
- **Почему HTTP-ошибки проверяются отдельно от сетевых:** `fetch` отклоняется только при сетевом сбое, а ответ 404 или 503 для него успешен. Нужно отличать «сервер ответил отказом» (есть статус и, возможно, код и детали) от «ответа нет» (нет связи, тайм-аут, отмена); пользователю и коду требуются разные действия.
- **Почему JSON после разбора проверяется по контракту:** корректный синтаксис не гарантирует нужную структуру. Сервер может вернуть массив вместо объекта, повторяющиеся id или неверный `meta.total`; приложение не должно принимать такие данные как достоверные.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `parseBaseUrl` разбирает значение через `URL`: допускаются только `http` и `https`, без query и hash; конечные слэши базы и ведущие слэши пути убираются, поэтому двойной `/` не появляется | Проверки клиента 01, 04 |
| Кодирование query-параметров | Параметры добавляются через `URLSearchParams.append`; `undefined`, `null` и `""` пропускаются, `false` и `0` сохраняются; входной объект не изменяется | 02, 03; собственная O8 |
| Заголовок `Accept` | `Accept: application/json` в каждом запросе | 05 |
| Проверка `response.ok` | До разбора тела: при ошибке читается payload `error` (если это JSON) и создаётся `ApiError` вида `http` с `status`, `code`, `details`, `url` | 08, 09, 16; интеграционные 07–09 |
| Проверка `Content-Type` | У успешного ответа тип должен быть `application/json` (допускается `+json`), иначе `invalid-response`; для 204 возвращается `null` | 07, 10; интеграционная 11 |
| Разбор JSON | `response.json()` в отдельном `try`; `SyntaxError` превращается в `invalid-response` с сохранением `cause` | 11; интеграционная 10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`; отказ по тайм-ауту определяется по состоянию сигнала и получает `kind: timeout` | 14; интеграционная 12 |
| Внешняя отмена | Внешний сигнал объединяется с тайм-аутом через `AbortSignal.any`; если он сработал, `kind: aborted` | 15; интеграционная 13; собственная O5 |

Вид отказа определяется по состоянию сигналов, а не по тексту сообщения: порядок проверки такой — внешняя отмена, затем тайм-аут, иначе сетевая ошибка. `ApiError`, созданный при обработке ответа, не попадает в блок `catch` для `fetch`, поэтому не маскируется как `network` (проверка 16).

## Доменный модуль задач

Результаты получены запуском `npm run example:domain`.

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id `[1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34]`, `meta.total = 12` |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id `[4, 13, 34]`, `meta.total = 3` |
| `getTaskById(25)` | `{ id: 25, title: 'Исправить обработку ошибок', completed: true, priority: 'high', categoryId: 2 }` |
| `getCategories()` | `1 = Учёба`, `2 = Проект`, `3 = Организация` |
| `loadInitialData({ completed: false, priority: "high" })` | Объект с ключами `tasks` (id `[4, 13, 34]`), `categories` (3 записи) и `meta` (`total = 3`) |

Правила проверки:
- **Задача:** `id` — положительное безопасное целое; `title` — строка, непустая после `trim()`, не длиннее 100 символов; `completed` — булево; `priority` — `low`, `medium` или `high`; `categoryId` — положительное безопасное целое (`null` недопустим).
- **Категория:** `id` — положительное безопасное целое; `name` — непустая строка.
- **Уникальность id:** повторяющиеся `id` в коллекции — `invalid-response`.
- **`meta.total`:** должно быть равно длине `data`; для задач `meta.filters` — объект.
- **Фильтры запроса** (до обращения к сети): допустимы только `completed` (булево), `priority`, `categoryId` (положительное целое), `q` (строка до 100 символов после `trim()`); неизвестные ключи и неверные значения дают `TypeError`.

## Последовательная и параллельная загрузка

Два независимых запроса `/debug/delay?ms=150`, `npm run example:parallel`.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 357 | 307 | 307 | Время близко к сумме двух задержек (2 × 150 мс) |
| `Promise.all` | 154 | 156 | 155 | Время близко к одной задержке (150 мс) |

При последовательной загрузке второй запрос начинается только после ответа на первый, поэтому задержки складываются. В `Promise.all` оба запроса уже начаты до общего `await`, их ожидание перекрывается, и общее время определяется самым медленным. Это справедливо для независимых запросов. Если второй запрос зависит от результата первого, параллельно их начать нельзя. Значения зависят от компьютера, в выводе не утверждается точное ускорение для любых условий.

## Вывод

В ПР5 реализован слой работы с сервером: общий клиент `requestJson` и предметный модуль задач поверх него. Клиент отличает шесть случаев: ожидание `Promise` (обычная асинхронная операция), HTTP-ошибку (сервер ответил статусом 4xx/5xx, `fetch` при этом не отклоняется), сетевую ошибку (ответа нет, `kind: network`), неверный ответ сервера (не JSON, повреждённый JSON или нарушение схемы, `invalid-response`), тайм-аут (`timeout`) и явную отмену (`aborted`). Вид отказа определяется по состоянию `AbortSignal`, а не по тексту сообщения. Независимые запросы запускаются до общего `await`, что подтверждено измерением: последовательная загрузка ≈ 2 задержки, `Promise.all` ≈ 1 задержка. Эксперимент с очередями показал, что микрозадачи (`then`, продолжение после `await`) выполняются до задач таймера даже с задержкой 0. Самой показательной оказалась проверка граничных случаев: допуск названия в 101 символ в ответе сервера не заметили готовые проверки, но заметила собственная.
